# コメントのルール

対象はソースコードと設定ファイルのコメント。散文として読ませるファイル（README、設計ドキュメント）のコメントは定義しない。

**原則としてコメントは書かない。** 実装と一緒に更新されず必ず乖離し、乖離したコメントは無いより有害。補足が要るなら、先に名前・分割・型で表す。

## 残してよいもの

リポジトリ内を全部読んでも分からず、理由がコードの外にあるものだけ。迷ったら書かない。

- **外部の仕様・ライブラリの都合。** 例: 決済APIは失敗時も 200 を返し、body の error で判別する
- **一見不要なコードが必要な理由。** 次の人が消さないためのもの
- **意図的に書いていないこと。** 例: display はユーティリティクラス側に統一しているのでここで指定しない
- **名前から意味が読み取れない値。** 例: `'-'` は初期状態が閉、`'+'` は開

`@ts-expect-error` `eslint-disable` `# noqa` などのディレクティブはコードなので対象外。ただし抑制の理由は併記する。

「なぜ」を1〜2行で書く。それ以上要るなら、命名や構造で表し直す。実装を変えたらコメントも直すか消す。
