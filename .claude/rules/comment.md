# コメントのルール

**原則としてコメントは書きません。** コードを読めば分かることは、コメントではなくコードで表現します。

コメントは実装と一緒には更新されず、必ず実装から乖離します。乖離したコメントは無いより有害なため、
「無くても困らないコメント」は最初から書かない、という方針を取ります。

対象はソースコードと設定ファイルです。散文として読ませることが目的のファイル（記事本文、設計ドキュメント、
README）は対象外です。

---

## 1. 書かないもの

| 種類 | 削除例 | 理由 |
| :--- | :--- | :--- |
| コードの言い換え | `// ユーザーをIDで取得する` の直後に `findUserById(id)` | 直後の1行が同じことを言っている |
| セクションラベル | `// --- 初期化 ---` `<!-- Header -->` `# --- helpers ---` | 直後の関数名・タグ名・クラス名で分かる。区切りが要るなら分割する |
| 型やシグネチャで分かること | `@param id ターゲット要素のID`<br>`/** ページ固有のタイトル */ title?: string` | 型定義が正。二重管理になる |
| 推測できる背景 | `/* ヘッダー64px + 余白24px */`（`88` という値に対して） | 実装を追えば辿り着ける。値の内訳を残したいなら名前付きの定数に切り出す |
| 他ファイルの場所案内 | `// この値は〇〇側で一元管理している` | grep で分かる。参照先が動いた瞬間に嘘になる |
| 処理ブロックの要約 | `// 一覧を取得し、期限切れを除外して、更新日時の降順に並べる` | 関数・変数の命名で表現する |
| コメントアウトされたコード | `// { label: 'About', path: '/about' },` | Git 履歴が持っている |
| ツール由来の定型コメント | scaffold やジェネレータが吐いたドキュメントURL・TODOの雛形 | 読まれない残骸 |
| キー名と重複する用途説明 | 設定オブジェクトの各キーに付けた `/** 背景色 */` 等 | `bg` `border` `accent` というキー名が用途そのもの |

## 2. 残してよいもの

以下に当てはまる場合**のみ**書きます。判断に迷うものは書かない側に倒します。

### 2.1 外部の仕様・ライブラリの都合

リポジトリ内を全部読んでも分からず、外部の知識が要るもの。ドキュメント側に同じ記述があっても、コード側に残します。

```ts
// 決済APIは失敗時も 200 を返し、bodyのerrorで判別する仕様
if (res.error) { ... }
```

```ts
// 外部APIのレート制限が 60req/min
const INTERVAL_MS = 1_000
```

```css
/* フレームワークのリセットCSSが付ける余白をここで打ち消す */
```

### 2.2 一見不要に見えるコードが、必要な理由

消してよさそうに見える行を、次の人が消さないためのもの。

```ts
// 対象が既に条件を満たしていてイベントが一度も発火しないケースの保険
settle()
```

### 2.3 意図的に「書いていない」こと

コードに現れないため、コメントでしか表現できないもの。

```css
/* 表示・非表示の切り替えはユーティリティクラス側に統一しているため、displayはここで指定しない */
```

### 2.4 名前から意味が読み取れない値

```ts
// '-' は初期状態が閉、'+' は初期状態が開
fold?: string
```

```ts
// 例: "github action" -> "github-action", "@scope/pkg" -> "scope-pkg", "S3" -> "s3"
export function toSlug(input: string): string
```

### 2.5 機能を持つディレクティブ

`@ts-expect-error` `eslint-disable` `# noqa` `#[allow(...)]` など、ツールが解釈するものはコメントの形をした
コードなので、この規約の対象外です。ただし抑制の理由は併記します。

```ts
// @ts-expect-error 型定義のないローカルモジュール
```

## 3. 書くときの書き方

- **「何を」ではなく「なぜ」を書く。** ただし §1 のとおり、リポジトリ内を読めば分かる「なぜ」は書かない。書くのは外部要因だけ。
- **1〜2行に収める。** それ以上の説明が必要なら、コードコメントではなくドキュメントに書く。
- **実装を変えたらコメントも直すか消す。** 残す価値が無くなったら消す。

## 4. 判定手順

1. そのコメントを消して、コードだけで意味が変わるか？ → 変わらないなら**消す**
2. リポジトリ内を読めば分かる内容か？ → 分かるなら**消す**
3. 命名の変更・定数の抽出・関数の分割で表現できるか？ → できるなら**そうする**
4. 外部（ライブラリ仕様、外部ツールとの互換、運用上の決定）を知らないと分からないか？ → §2 に当てはまるなら**残す**
